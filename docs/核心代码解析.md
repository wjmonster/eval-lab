## 一、config.py（66 行）：为什么是一家一张表

```python
"zhipu": {
    "base_url": "https://open.bigmodel.cn/api/paas/v4",
    "model": "glm-4-flash",
    "key_env": "ZHIPU_API_KEY",
}
```

三个字段就够了，因为国内这几家都提供 **OpenAI 兼容**接口，差别只有三处：地址、模型名、密钥变量名。所以 `llm.py` 里不需要 `if provider == "zhipu"` 这种分支——**加一家新厂商 = 往这张表加一条**，不改代码逻辑。

两个细节要记住：

- `key_env` 存的是**变量名**，不是密钥值。密钥永远在 `.env`（`llm.py:144` 用 `os.getenv(cfg["key_env"])` 取）。这样代码可以进 git，密钥不会。
- `PRICE_CNY_PER_MTOK`（55 行）**是占位值**。它的作用只是把"成本"这一列跑通，`estimate_cost_cny`（64 行）拿不到模型就算 0。写报告前必须按控制台实际单价改，否则成本结论是假的。

`qwen` 那条 base_url 特别长，不是笔误：百炼给每个账号一个业务空间专属域名（`ws-xxxx.cn-beijing.maas.aliyuncs.com`），老的 `dashscope.aliyuncs.com` 2026-09-30 起进维护。

## 二、llm.py 第 33-39 行：什么错误值得重试

```python
RETRYABLE = (
    httpx.TimeoutException,        # 网络慢 / 服务端卡住
    httpx.TransportError,          # 连不上
    openai.APIConnectionError,     # SDK 层连接问题
    openai.RateLimitError,         # 429
    openai.InternalServerError,    # 5xx
)
```

**这张表本身就是设计**：400（参数错）、401（key 错）**故意不在里面**——重试它们等于浪费 4 次请求换同一个错误。而 429、超时、5xx 属于"现在不行，等会儿可能行"，才值得再试。

面试点：这个元组决定了重试的边界。加错一个类型（比如把 `APIError` 基类整个放进来），就会把"你参数写错了"也重试 4 次。

## 三、llm.py 第 42-53 行：5 行代码，省掉一次白重试

```python
def retry_after_seconds(exc):
    resp = getattr(exc, "response", None)          # 异常里能不能拿到响应
    raw = resp.headers.get("retry-after")          # 服务端让你等几秒
    return max(0.0, float(raw))
```

为什么值得单独写：服务端说"等 2 秒"，而你的退避只等 1 秒就冲上去——**这次尝试必输**，白烧一次。D3 实测第一次等待正好 2.00 秒、服务端收到的间隔也是 2.00，这就是它生效的证据。

它还做了两层防御：异常没有 `response` 属性（比如纯网络错误）返回 `None`；header 不是数字（有些服务给日期格式）也返回 `None`，绝不抛异常把重试逻辑搞崩。

## 四、llm.py 第 56-78 行：一条记录该有哪些字段

`CallRecord` 17 个字段，每个都对应一个后面会用到的问题：

| 字段 | 不写它会怎样 |
|---|---|
| `case_id` | 分不清这条是哪道题的结果，没法按用例聚合 |
| `provider` / `model` | 换模型后分数变了，你说不清是谁变的 |
| `prompt_version` | 改了 prompt 之后，新旧数据混在一起比，结论是假的 |
| `temperature` / `max_tokens` | 同上，参数变了必须能筛 |
| `prompt` | 出问题时无法复现 |
| `output` | 没有原文，judge 判错了你没法复核 |
| `input_tokens` / `output_tokens` | 算不出成本，也发现不了"prompt 悄悄变长" |
| `latency_ms` | 无法回答"这次是不是变慢了" |
| `cost_cny` | 无法设预算，也无法回答"这个评测贵不贵" |
| `attempts` | 分不清"模型错"和"被限流"——这是最关键的一个 |
| `finish_reason` | 分不清"正常答完"和"被 max_tokens 截断" |
| `error` | 失败率、失败原因是空的 |
| `ts` / `run_id` | 没法按批次对比，也没法把同一次运行的记录串起来 |
| `retry_waits_s` | "退避够不够"只能靠感觉 |

`attempts` 值得单独说：它是**归因的分界线**。`attempts=4 且 error=RateLimitError` → 是限流，不是模型不行；`attempts=1 且 output 正常但内容错` → 才是模型的问题。

## 五、llm.py 第 148 行：`max_retries=0` 是最容易被忽略的一行

```python
client = OpenAI(base_url=..., api_key=..., timeout=timeout_s, max_retries=0)
```

openai SDK **自己带重试**（默认 2 次）。不关掉会发生什么：

- SDK 内部先重试 2 次（你完全看不见）
- 你的 tenacity 再重试 4 次
- 实际打出去的请求 = 4 × 3 = **12 次**，但 `attempts` 只记到 4

结果：限流时你以为打了 4 次，实际打了 12 次；`attempts` 这个字段直接失真。所以必须 `max_retries=0`，**重试只由一层负责，而且这一层必须是你自己的**。

这条是"可观测性优先于省事"的典型取舍。

## 六、llm.py 第 153-183 行：三个函数决定了重试的全部行为

### `_wait`（153 行）：等多久

```python
base = wait_exponential_jitter(initial=1, max=20)(retry_state)  # 1→2→4→8，带抖动
ra = retry_after_seconds(exc)                                   # 服务端要求的下限
if ra is not None:
    base = max(base, ra)                                        # 两者取大
waits.append(round(base, 2))                                    # 记下来，别靠感觉
```

三个动作各有目的：指数增长防雪崩、抖动防"所有客户端同一秒一起冲"、`max(base, ra)` 保证不早于服务端要求。最后那个 `append` 是**给证据留的**——不然"退避够不够"永远只能靠感觉。

### `_stop`（163 行）：什么时候放弃

```python
if retry_state.attempt_number >= max_attempts: return True   # 出口一：次数
return (time.time() - t0) > budget_s                          # 出口二：总耗时
```

只有次数出口的话，一条卡死的请求能拖很久（D3 实测：1 秒超时 × 4 次 = 11.42 秒）。加预算出口后同样的场景 3 次就停。

**但要诚实说它的缺陷**：预算是在"下一次尝试起跑前"判断的。第 3 次起跑时累计约 4 秒（没超 5 秒预算），跑完加上等待才超——所以 5 秒预算实际跑了 6.97 秒。**要按预算的 1.4 倍预留**。这个数字是量出来的。

### `_do`（175 行）：真正的请求

```python
attempts += 1                       # nonlocal，注意这行在发请求之前
return client.chat.completions.create(model=..., messages=[...], temperature=..., max_tokens=...)
```

`attempts` 在发请求**前**自增，所以即使第一次就失败，`attempts` 也是 1 而不是 0——"尝试过 1 次"和"没尝试"在统计上必须分开。

## 七、llm.py 第 199-209 行：为什么 `except Exception` 而不只捕可重试错误

```python
except Exception as e:   # 真实调用失败也要落库，否则你永远不知道失败率
    rec = CallRecord(..., attempts=attempts, finish_reason="error",
                     error=f"{type(e).__name__}: {str(e)[:120]}")
```

如果这里只写 `except RETRYABLE`，那么 400、401、坏 JSON 这类"不可重试"的错误会**直接抛穿**，`_log` 不会执行——结果就是：你的数据里只有成功的调用，失败率永远是 0。

这是评测里最隐蔽的一种谎言：**分母悄悄变小**。

`error` 截断到 120 字也必要——有些 SDK 异常带整个响应体，不截断会把 jsonl 撑爆。

## 八、llm.py 第 214-232 行：`parse_json_lenient` 三档降级

```python
for candidate in (text, *围栏内容):      # 第 1 档：原文 / 去掉 ```json 围栏
    json.loads(candidate)
start, end = text.find("{"), text.rfind("}")   # 第 2 档：截取第一个 { 到最后一个 }
frag.replace("'", '"')                          # 第 3 档：单引号改双引号再试
return False, None                              # 全失败 → 明确返回 False
```

为什么必须这么写：模型的"结构化输出"经常是这样——带 ````json` 围栏、前后有"好的，结果如下："、用单引号、甚至根本不给 JSON。直接 `json.loads` 会让整批评测崩在解析上，而不是给出一个分数。

**关键设计**：失败时返回 `(False, None)` 而不是抛异常。让调用方决定"解析失败算 0 分还是算 error"，这是评测语义问题，不该由工具层替你决定。

注意这是"**宽松解析**"，不是"修复"。它不补括号、不猜字段。补不了就老实返回 False——别让兜底变成掩盖数据质量问题的工具。

## 九、cli.py：两张表的口径

```python
statistics.median(lat)          # 79 行：用中位数，不用均值
sum(1 for r in rs if r.error)   # 81 行：失败单独计数，不混进延迟
```

为什么中位数：D2 实测 siliconflow 延迟 344 → 4374 ms，均值会被那一个尖刺拉高，中位数不会。**只报均值等于让异常值替你说话。**

为什么失败单独一列：失败调用的 latency 是"等到超时/重试耗尽的时间"，把它算进平均延迟，延迟指标就变成"故障率指标"了。

`45 行`的 `except RuntimeError` 只捕"缺 key"，跳过这家继续跑——**一家没配不该让整批挂掉**。

## 十、faults.py：拿 model 名当"故障开关"

```python
model = str(payload.get("model", "fault-ok"))     # 84 行
if model.startswith("fault-429"): ...             # 95 行
if model.startswith("fault-flaky"): limit = int(model.rsplit("-", 1)[-1])   # 102 行
```

为什么不给每种故障开一个端口/路径：**切换场景只需要改一个字符串**，而且请求体格式和真实厂商完全一致——这意味着被测代码不需要为测试写任何分支，测的就是线上那条路。

`REQUESTS.append({"t": time.time(), ...})`（89 行）是这套设计的关键：服务端自己记时间戳，于是"客户端说等了 2 秒"能和"服务端实际隔了 2 秒"对账。**单一视角的证据不可信，两个视角对上才算。**

## 十一、tests/test_llm.py：三个测试各守一条底线

| 测试 | 守的是什么 |
|---|---|
| `test_mock_call_records_everything` | 每次调用必须让 jsonl **多一行**，且字段齐全 —— 落库契约 |

## 十二、代码里四个可以直接讲的取舍

1. **关掉 SDK 自带重试，自己实现一层** → 换来了 `attempts` 可观测（否则 4×3 次真实请求只记 4）
2. **失败也落库** → 分母正确，失败率算得出来（否则数据里只有成功样本）
3. **预算判在起跑前，接受 1.4 倍溢出** → 简单可预测，而不是精确但复杂
4. **mock 是一等 provider** → 没 key 也能验完整链路（落库/超时/统计），接手第一天就能跑
