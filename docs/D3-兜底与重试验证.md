# D3 兜底与重试验证：把故障打进真实链路

**日期**：2026-11-18　**命令**：`uv run eval-lab faults`　**明细**：`results\d3_faults.json`

## 一、为什么 D3 要重做一遍

`simulate.py` 里的 429 场景是这么写的：

```python
raise RateLimitError("429 Too Many Requests")   # 在内存里假装抛异常
```

它验证的是 tenacity 的配置，**没验证**下面这些真正会出事的地方：

- httpx 收到 429 时，openai SDK 到底抛哪种异常？我们的 `RETRYABLE` 元组认不认？
- 服务端给了 `Retry-After: 2`，我们等够了吗？还是自己瞎猜 1 秒就重试，结果又吃一个 429？
- 超时是"每次 60 秒 × 4 次"吗？一条卡死的用例会占住多久？
- 返回 200 但 body 是坏 JSON——客户端会崩，还是落一条 error？

这些只有在**请求真的落到 socket 上**才成立。所以 D3 的做法是：本地起一个 OpenAI 兼容的故障服务器，让 `call_llm` 走线上同一套代码。

## 二、怎么做的

`src/eval_lab/faults.py`：进程内起 `ThreadingHTTPServer`（127.0.0.1:8791），按 model 名决定行为：

| model 名 | 行为 |
|---|---|
| `fault-ok` | 200 正常 |
| `fault-flaky-N` | 前 N 次 429，第 N+1 次成功 |
| `fault-429` | 永远 429，带 `Retry-After: 2` |
| `fault-slow` | 睡 3 秒再回 200（配 `--timeout 1` 就是真超时） |
| `fault-500` | 永远 500 |
| `fault-badjson` | 200，但 body 是 `{this is not json at all` |

服务器把每次请求的时间戳记下来，所以"退避到底等了多久"有**两个视角**：客户端的 `retry_waits_s`，和服务端收到的相邻请求间隔。两者对得上，才说明等待是真的发生了。

## 三、结果（7 个场景全部 PASS）

| 场景 | attempts | 客户端等待(s) | 服务端请求间隔(s) | 耗时(s) | 结果 |
|---|---|---|---|---|---|
| 正常 200 | 1 | — | — | 0.64 | 正常响应 |
| 前 2 次 429 后成功 | 3 | 1.19 / 2.91 | 1.20 / 2.91 | 4.13 | 第 3 次拿到内容 |
| 持续 429 | 4 | 2.00 / 2.41 / 4.27 / 8.00 | 2.00 / 2.42 / 4.28 | 8.71 | `RateLimitError` 落库 |

| 持续 500 | 4 | 1.48 / 2.01 / 4.78 / 8.59 | 1.49 / 2.01 / 4.78 | 8.30 | `InternalServerError` 落库 |

## 四、四条发现（都是量出来的，不是推的）

### 1）`Retry-After` 原来是被忽略的

改之前，退避是一刀切的 `wait_exponential_jitter(initial=1, max=20)`，服务端说"等 2 秒"，客户端可能 1.1 秒就冲上去重试，**白烧一次尝试**。

改之后第一次等待是 **2.00 秒**，正好等于服务端要求的 `Retry-After: 2`——客户端的 `2.00` 和服务端收到的间隔 `2.00` 对上了。这条就是"改之前会多失一次"的证据。

### 2）退避序列是真的在涨：2.0 → 2.4 → 4.3 → 8.0

符合指数退避 + 抖动。但要看清代价：**一次持续 429 的调用要占 8.7 秒**。100 条用例串行跑，遇到限流就是 14 分钟；所以批量评测必须并发 + 总预算，不能只靠"重试 4 次"。

### 3）超时场景最恶劣：单次 11.4 秒，而且预算会溢出

- 1 秒超时 × 4 次 + 退避 = **11.42 秒**，只换来一条失败记录
- 加上 5 秒预算后截断到 3 次、6.97 秒——但还是**超出了 5 秒预算**

原因是预算只在"下一次尝试起跑前"判断：第 3 次起跑时累计约 4 秒（没超预算），跑完 + 等待后才超过 5 秒。**所以工程上要按预算的 1.4 倍左右预留**，别把 5 秒预算当成"最多 5 秒"。

### 4）坏 JSON 不重试，落 error 不崩

`JSONDecodeError` 不在 `RETRYABLE` 里，所以 `attempts=1`、0.01 秒就结束了，写了一条 error 记录，**进程没崩**——这是对的，崩了整批用例就全没了。

但有个值得记一笔的细节：**返回 200 却 body 坏**，通常不是模型的问题，而是网关/代理返回了错误页。这种情况给 1 次重试更合理。这条先记成待办，不擅自改（改了就要重跑全部场景）。

## 五、这次改了哪几处

| 文件 | 改动 | 为什么 |
|---|---|---|
| `llm.py` | 新增 `retry_after_seconds()`，重试等待取"指数退避"和 `Retry-After` 的较大值 | 服务端说什么就等什么，别猜 |
| `llm.py` | 新增 `budget_s` 总预算，与 `max_attempts` 双出口 | 防一条死请求拖住整批 |
| `llm.py` | `CallRecord.retry_waits_s` 记录每次等待 | 没有这个数字，"退避够不够"就永远是感觉 |
| `llm.py` | `model_override` 参数 | 让同一 provider 能跑不同故障模型 |
| `config.py` | 新增 `fault` provider 指向 `127.0.0.1:8791` | 本地故障服务器入口 |
| `faults.py` | 新增（服务器 + 探针 + 判定） | D3 主体 |
| `cli.py` | 新增 `eval-lab faults`；`compare --budget` | 一条命令跑完 D3 |

回归：`uv run pytest -q` → **3 passed**；`uv run eval-lab simulate` → 三个老场景仍 PASS。

## 六、D3 判定

- 429 / 超时 / 5xx / 坏 JSON **四类故障都在真实 HTTP 链路上复现并被处理住**，7/7 PASS
- 重试次数、等待时长、预算截断三件事有了**可核对的数字**（客户端等待 ↔ 服务端间隔互相印证）
- 失败一律落库（`finish_reason=error` + `error` + `attempts`），批量跑不会因为一条失败中断

**这段面试怎么讲**（30 秒版）：
> 我没在内存里 mock 异常，而是起了一个 OpenAI 兼容的故障服务器，把 429、5xx、超时、坏 body 打进真实 SDK 链路。量出来两件事：一是我原来的退避忽略了服务端的 `Retry-After`，会导致多烧一次尝试；二是一条持续 429 的调用要占 8.7 秒，所以只加"重试 4 次"不够，必须同时加总预算，而且预算判在起跑前，实际会溢出到 1.4 倍。
